## What this tool is

`uv-matrix` is a thin **matrix runner for uv-based Python projects**. It expands named matrices, maps each (cell, task) to a `uv run ...` invocation, runs them, and summarizes failures. It deliberately delegates Python install, venv creation, dependency resolution, and lockfile sync to `uv` — do not reimplement those. (Unrelated to UV coordinate transforms in graphics.)

Scope is intentionally narrow: read config → expand matrices → map task to `uv run` → aggregate results. Anything beyond that (installer/virtualenv backends, conda, tox/nox compat, plugins) is explicitly out of scope.

## Commands

This is a uv project — use `uv`, not bare `pip`/`python`.

- `uv sync` — create/sync the environment from the lockfile
- `uv run uv-matrix` — run the console entry point (`uv_matrix:main`)
- `uv build` — build with the `uv_build` backend

- `uv run pytest` — run the test suite (`tests/`)

No lint/type setup exists yet; add one when needed.

## Design constraints to honor when implementing

These shape the public config contract and are derived from the current implementation:

- **Config: two namespaces under `[tool.uv-matrix]`**: top-level `continue-on-error`/`max-jobs`/`env`/`envfile` (+ optional `[tool.uv-matrix.vars]`); **named matrices** `[tool.uv-matrix.matrix.<name>]` (axis arrays + the reserved keys `tasks` and `exclude`); **task definitions** `[tool.uv-matrix.tasks.<name>]` (`TASK_DEFS_TABLE = "tasks"` — it deliberately shares the spelling of the matrix reserved key so there is one word to remember; the two live in different parent tables). Tasks are reusable across matrices. There is no unnamed default matrix and no `task` axis — that older model is gone. (`fail-fast` and the singular `task` table were removed.) Unknown keys are rejected up front (`validate_config_names`): a typo at the top level of `[tool.uv-matrix]` or in a task table (e.g. `group` for `groups`) is a `ConfigError`, never silently ignored.
- **Names are validated**: matrix names, axis names, and `vars` keys must follow Python's variable rules with `-` also allowed (`config._is_valid_name`: the name with `-`→`_` must be an identifier and not a keyword). Each matrix axis and each `vars` key is also injected into the evaluation context as a **top-level variable** with `-` replaced by `_` (`{{ python_version }}` for the `python-version` axis), while the `matrix['...']`/`vars['...']` dict lookups keep working. Precedence on a name clash: reserved context names > matrix axes > vars. Two axes in one matrix that collapse to the same underscore alias (e.g. `a-b` and `a_b`) are an error.
- **Expansion (`config.iter_plan`)**: for each named matrix, every key except the reserved `tasks`/`exclude` is an axis; cartesian-product the axes (`expand_matrix`) and pair each cell with each name in `tasks`, yielding `(matrix_name, cell, task_name)`. Matrices are independent (a task in two matrices runs in each; a matrix with only `tasks` runs each task once). **Matrix-level `exclude`** (issue #4) is an array of tables; a cell matching all `key = value` pairs of any rule is dropped before pairing with tasks. Each rule key must be an axis name and each value must be one of that axis's values — a rule that could never match any cell is an error, not a silent no-op. `resolve_job(config, matrix_name, cell, task_name, task_defs, posargs)` builds the `Job`; a false `when` → skipped (`None`).
- **Per-field evaluation kind is fixed**, not inferred from the string:
  - template (**Jinja2**, `{{ ... }}`): `python-version`, `run` (the string form whole; each element of the exec-form array), `groups`/`extras`/`uv-args` (each list item), `env` (values), `envfile` (paths), `cwd`. All renders share one environment (`evaluate._JINJA`) with `StrictUndefined` (a missing name is an error, not an empty string), autoescape off, and a `finalize` that renders `None` and `False` as `""` (`0` is untouched).
  - expression (Python `eval`): `when`, `continue-on-error` when it's a string (a bool is used literally), and top-level `vars` values when they are strings (non-strings are used literally; quote a literal string: `reports = "'.reports'"`). Vars evaluate in definition order inside `build_context` — each sees the reserved names, the matrix cell's axes, and earlier vars; `environ` there is the plain process environment (vars resolve before `envfile`/`env`).
  - literal (never evaluated): `matrix` axis values.
- **List-field element dropping (`groups`/`extras`/`uv-args`)**: `runner._rendered_list` renders each element with the normal string render, strips it, and drops it when nothing remains — so a bogus flag like `--group ""` is never built. Because the Jinja `finalize` renders `None`/`False` as `""`, `"{{ cond and 'web' }}"` is omitted when `cond` is false with no `or ''` needed. There is no separate native-eval render. This dropping does **not** apply to the exec-form `run` array (see the mapping bullet below), where an empty render is kept as an empty argument.
- **Job environment (`env`/`envfile`)**: both settings exist at the top level `[tool.uv-matrix]` (applied to every job) and per task. Per job the layers merge low→high: `os.environ` < top-level `envfile` < top-level `env` < task `envfile` < task `env` — so within a level `env` wins over `envfile`, and a task's settings override the top-level ones for that task's jobs only. `envfile` paths and `env` values are templates; after each step the merged result is folded into `environ`, so a task-level template can read top-level values and every later field (`when` included) sees the post-override environment. A missing `envfile` is an error, not a silent skip.
- **Failure handling (`continue-on-error`)**: effective value per job = task's own `continue-on-error` if set, else global `[tool.uv-matrix] continue-on-error`, else `false`. A failing job whose effective value is `false` stops the run (sequential: break; parallel: cancel not-yet-started jobs, let running ones finish); `true` continues with the rest. Either way a non-zero exit always counts toward the final exit code — there is no exit-code suppression / "allowed failure" concept (removed along with `fail-fast`).
- **Evaluation context** (`evaluate.build_context`) exposes: `matrix` (the matrix cell dict), `matrix_name`, `vars` (the global `[tool.uv-matrix.vars]` table with its string values already expression-evaluated; task-local `vars` are ignored), `task` (name), `task_config` (the task's dict), `posargs` (the CLI arguments after `--`, shell-quoted and space-joined into one string; `""` when absent), `environ` (a copy of `os.environ`, updated as `envfile`/`env` layers apply), `platform` (`sys.platform`), plus the underscore-alias top-level variables for axes and vars described above.
- **Reserved `python-version` axis**: `python-version` is a reserved matrix axis name. A task with no `python-version` of its own inherits the matrix cell's `python-version` value (used literally, not as a template); a task that sets `python-version` overrides it (rendered as a template). When neither supplies one, `python_version` is `None` and the command omits `--python` so uv picks its default interpreter.
- **Task → command mapping**: `python-version` → `uv run --python`, each `groups` entry → `--group`, each `extras` entry → `--extra`, each `uv-args` entry inserted verbatim as a `uv run` flag (for `--with`, `--no-default-groups`, etc.), `run` comes last and has two forms, told apart by TOML type (`Job.shell` records which; `spawn_args(command, shell)` applies its Windows string-join to shell-form jobs only). **Shell form** (string): wrapped for the platform's shell after the uv flags (`runner._shell_command`: `sh -c` on POSIX, `%COMSPEC% /c` on Windows) so `run` is shell-interpreted inside the uv environment; the parent process never uses `shell=True`. **Exec form** (array, `runner._exec_command`): each element renders to exactly one argv element — no stripping, an empty render is kept — placed after a `--` that stops uv's flag parsing; no shell is involved. An element that is exactly `{{ posargs }}` (surrounding whitespace allowed) is spliced with the raw post-`--` CLI arguments, zero elements when absent; an embedded `{{ posargs }}` renders the joined string as usual. An argv that resolves empty is a `TaskError`.
- **Job selection (`run` and `list`)**: both subcommands select through `cli._selected` — `--matrix`/`--task` match by exact name and an unknown name is an error, and repeatable `--filter KEY=VALUE` is validated against the axes by `config.parse_filters` (unknown key or value → error; OR within a key, AND across keys). Errors over silent no-matches, so a typo never quietly selects nothing. `list` is a selection aid only: it expands the matrices but never renders templates or evaluates `when`. `run` also takes `--dry-run` (print banners and commands without running) and passes arguments after `--` to templates as `{{ posargs }}`.
- **Parallelism and verbosity (CLI)**: `--max-jobs N` overrides the top-level `max-jobs` (default 1 = sequential, stdio inherited and streamed live; parallel runs capture each job's output and print it as one block per job). Net verbosity is `-v` count minus `-q` count: below `-vv`, uv gets `--quiet` so its sync chatter stays hidden; at `-vv` uv keeps its default output, and further `-v`s are forwarded to uv. `-q` suppresses banners; color is disabled by `--no-color`, `NO_COLOR`, or a non-TTY stdout.
- **Per-slot environment isolation (always on)**: each job runs with `UV_PROJECT_ENVIRONMENT` set to `<project-root>/.uv-matrix/slot-<n>` (`cli._slot_dir`), one directory per parallel slot; sequential runs use slot 0. This keeps `.venv` untouched, and uv's implicit sync reconciles the slot's directory to each job's requested contents (python-version/groups/extras/uv-args), so jobs never share env state. `cli._job_env` layers it under the task's own `env` (explicit task env wins). There is no toggle — isolation is unconditional. `.uv-matrix/` is gitignored. There is deliberately no content-keyed (`env_key`) naming: directory count stays bounded by `max-jobs`, at the cost of a re-sync when consecutive jobs on a slot differ (cheap via uv's hardlink cache on non-Windows).
- **Parallel runs use per-slot environments, no locks**: `_run_parallel` lends each running job a slot index (0..N-1) from a queue and returns it on completion. Concurrent jobs therefore never target the same directory, so identical-environment jobs run fully in parallel with no lock and no sync/run split (issue #24).
- **Object form** (`{ template = ... }` / `{ expr = ... }`) is deferred — don't build it yet.

## Security boundary

`run` executes arbitrary commands and templates/`when` are evaluated as Python. This is a trusted-repo developer tool, not a safe sandbox — keep that boundary explicit (and documented in the README) rather than trying to sandbox.
